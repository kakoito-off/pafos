# PAFOS — Pure And Fast OS

**PAFOS** (Pure And Fast OS) — официальное название проекта. Имя крейта — `pafos`.

Учебная микро-ОС на Rust для x86_64, запускается в QEMU.

Базируется на коде из цикла статей [Writing an OS in Rust](https://os.phil-opp.com)
(Philipp Oppermann), взята как отправная точка состояние после поста
"Heap Allocation" (freestanding binary → VGA text mode → testing →
CPU exceptions → double faults → hardware interrupts → paging → heap
allocation). Далее разрабатывается самостоятельно: шелл с набором
опциональных "микропрограмм" (калькулятор и т.п.), подключаемых в
сборку через Cargo features.

## Требования

- Rust nightly с GNU-toolchain (`nightly-x86_64-pc-windows-gnu` на Windows)
  и компонентами `rust-src`, `llvm-tools-preview`
- MinGW-w64 GCC в PATH (нужен хост-линкер для сборочных зависимостей)
- [`bootimage`](https://github.com/rust-osdev/bootimage) (`cargo install bootimage`)
- [QEMU](https://www.qemu.org/)

## Сборка и запуск

```powershell
.\build.ps1   # только собрать образ
.\run.ps1     # собрать и запустить в QEMU
```

Оба скрипта сами выставляют PATH, так что работают из любого открытого
терминала без ручной настройки окружения.

Аргументы скриптов передаются cargo, так выбирается набор программ:
`.\run.ps1 --no-default-features --features shell,calc`. Голый
`cargo bootimage` при переключении на уже собранный ранее набор фич может
оставить в образе старое ядро (загрузчик пересобирается по времени
изменения файла ядра, а cargo восстанавливает его со старой датой) —
скрипты это обходят, поэтому собирать лучше через них.

## Тестирование

```powershell
cargo test
```

Юнит-тесты и интеграционные тесты (`tests/`) гоняются прямо в QEMU
(headless, `-display none`), результат читается через serial-порт и
exit-код QEMU (`isa-debug-exit`).

## Что видно на экране при запуске

После инициализации (`init_core` + `init_memory`) ядро запускает оболочку
(`pafos> `). Команды: `help`, `echo <text>`, `clear`, `exit`, а также файловые:
`ls`, `cat <f>`, `create <f>` (создать пустой файл), `rm <f>`, `df` (занятость tmpfs),
`editfile <f> addline <text>` (дописать строку), `editfile <f> write <text>`
(заменить содержимое), `editfile <f> clear` (очистить). `editfile` работает
только с существующими файлами — создаются они только через `create`.
Всё остальное оболочка ищет как программу по имени (список — в `help`):
- `calc <выражение>` — целочисленный калькулятор (`+ - * / %`, скобки,
  унарный минус); `calc` без аргументов — интерактивный режим до `exit`/Ctrl+D;
- `time` — время работы системы (`pafos running 14 seconds`);
- `fault <режим>` — диагностическая программа, которая нарочно падает
  (`null`, `kernel`, `ud`, `hlt`, `panic`) или проверяет ядро (`badptr`,
  `heap`); ядро должно убить её и продолжить работу;
- `timer start | show | clear` — секундомер: `start` пишет метку
  `start <мс с запуска>` в файл `timer` (повторный `start` её перезаписывает),
  `show` печатает `timer now at 11 seconds`, `clear` удаляет файл.

Ctrl+C отменяет текущую строку, Ctrl+D (или `exit`) завершает оболочку —
ядро тут же запускает новую.

Про прерывания:
- **Таймер** (IRQ0, вектор 32): PIT перепрограммирован на ~100 Гц (по
  умолчанию ~18.2 Гц), `timer_interrupt_handler` считает тики (`clock.rs`).
  Наружу отдаются только миллисекунды с запуска — частота остаётся деталью ядра.
- **Клавиатура** (IRQ1, вектор 33): `keyboard_interrupt_handler` читает
  scancode из порта `0x60`, декодирует через `pc-keyboard` и **не печатает**,
  а кладёт символ в очередь ввода (`input.rs`). Оболочка забирает символы
  оттуда и сама решает, что выводить.

## Архитектура: ядро и программы

```
abi/            pafos-abi — единственный общий крейт ядра и программ:
                номера системных вызовов, коды ошибок, #[repr(C)]-структуры
libpafos/       библиотека программ (мини-libc): print!/println!, read_line,
                File, exec, uptime... Всё поверх одного raw::syscall
programs/*/     каждая программа — отдельный крейт, зависит только от libpafos
src/            ядро; syscall.rs — диспетчер, programs.rs — реестр программ
```

Программа — крейт с функцией `pub fn main(args: &[&str]) -> Exit`. Ядро
она не видит вообще (нет зависимости), так что разделение проверяет
компилятор. Ядро тоже не зависит от `libpafos` (только тесты — чтобы ходить
через системные вызовы, как программа).

Все обращения к ядру идут через `libpafos::raw::syscall(nr, [usize; 4])`,
результат — неотрицательное число или минус код ошибки. Строки и буферы
передаются парой (указатель, длина).

`raw::syscall` выполняет `int 0x80`: `rax` — номер вызова, `rdi`, `rsi`,
`rdx`, `r10` — аргументы, результат в `rax`, остальные регистры сохраняются
(как в Linux). В IDT на вектор `0x80` стоит trap gate с DPL 3, так что
вызов разрешён из ring 3 и не выключает прерывания (`exec` может длиться
долго). Ассемблерная заглушка `syscall::entry` сохраняет регистры и зовёт
диспетчер, передавая ему и уровень привилегий вызвавшего кода.

### Программы в ring 3

Все программы, включая `shell`, — отдельные исполняемые файлы: работают
в ring 3, каждая в своём адресном пространстве. В ring 0 работает только
ядро.

Исполняемая программа — бинарный крейт с `#![no_main]` и
`libpafos::entry!(main);`, `libpafos` с фичей `rt` даёт ей `_start`,
`exit`, обработчик паники и кучу 64 КиБ (в `.bss` самой программы).
У каждой программы своя фича `rt` (включает `libpafos/rt`), и бинарник
требует её (`required-features`): `build.rs` собирает его с `--features rt`,
а обычная сборка workspace бинарники пропускает. Так у `calc` может быть
ещё и библиотека (сам вычислитель без зависимостей), которую тесты ядра
проверяют напрямую, не таща в ядро второй обработчик паники.
`build.rs` ядра собирает такие программы вложенным cargo (в
`target/programs`, release) с линковкой по адресу `USER_BASE`, а
`programs.rs` вшивает ELF-файлы в ядро через `include_bytes!`.

Запуск (`process.rs`):
1. Разбор заголовков ELF, проверка, что все сегменты лежат в user-области.
   Аргументы копируются в кучу ядра: они могут лежать в памяти родителя,
   которая пропадёт после смены CR3.
2. Новая таблица P4: копия всех записей таблицы ядра (запомненной при
   загрузке, а не текущей — текущая может быть таблицей родителя) (прерывания и сисколы работают
   после смены CR3) плюс одна своя запись — user-область
   `0x6000_0000_0000` (512 ГиБ). Страницы ядра без флага USER, ring 3 их
   не видит.
3. Сегменты копируются через отображение физической памяти (в
   read-only-страницы ядро писать не может, CR0.WP); стек 64 КиБ под
   `USER_STACK_TOP`, аргументы — на его вершине (`rdi` = argc, `rsi` = argv).
4. Вход в ring 3 через `iretq`; регистры ядра обнуляются. Перед входом
   текущий указатель стека ядра записывается в TSS как RSP0 (см. ниже).
5. Возврат — по сисколу `EXIT` или при исключении процессора в ring 3
   (page fault, #GP, #UD, деление на ноль, ...): обработчик печатает
   `<имя>: killed (<причина>)` и возвращает родителю `Exit::Crashed`.
   В обоих случаях стек ядра восстанавливается из сохранённого при входе.
6. CR3 и RSP0 возвращаются родителю, все кадры процесса (страницы и таблицы)
   отдаются обратно аллокатору кадров (у него теперь есть список свободных).

Указатели из ring 3 диспетчер проверяет по таблицам страниц самой
программы (страница отображена, доступна ring 3 и, если ядро в неё пишет,
доступна на запись), так что программа не может заставить ядро прочитать
или испортить память ядра.

### Вложенный запуск

Многозадачности нет и не будет: `exec` синхронный, родитель ждёт, пока
потомок не завершится. Поэтому всем программам хватает одного стека ядра.
Когда программа вызывает `exec`, кадры этого сискола остаются на стеке
ядра, а потомок запускается прямо из них: RSP0 в TSS указывает чуть ниже,
так что прерывания и сисколы потомка ложатся под ожидающие кадры
родителя. На каждом уровне вложенности запоминается свой указатель стека
ядра; `EXIT` и падение всегда возвращают на самый внутренний уровень, где
ядро восстанавливает CR3 и RSP0 родителя и возвращает ему результат
`exec`.

```
стек ядра (растёт вниз)
  kernel_main → programs::run("shell")       уровень 1
  int 0x80 shell: exec("calc")               ← RSP0 для shell
  programs::run("calc")                      уровень 2
  int 0x80 calc: read_key                    ← RSP0 для calc
```

Глубина ограничена `MAX_NESTING` = 8 (ядро считается уровнем 0); девятый
`exec` получает `Error::TooDeep` ("too many nested programs").

Принцип: в ядре — механизм (небольшой набор вызовов в духе POSIX), удобства
— в `libpafos`. Если программе чего-то не хватает, сначала стоит попробовать
собрать это в `libpafos` из существующих вызовов.

```
kernel_main ── loop { programs::run("shell") }   // вернулась → новая; нет → hlt
   shell (ring 3) ── встроенные команды или exec(имя, аргументы) → реестр
```

Программы подключаются в сборку Cargo features (`shell`, `calc`, `time`,
`timer`, `fault`, все включены по умолчанию), например:
`.\build.ps1 --no-default-features --features shell,calc`. Ядро после
загрузки запускает `shell` по имени через тот же реестр; если оболочки в
сборке нет, оно очищает экран и просто простаивает в `hlt` (чёрный экран).
`cargo test` рассчитан на сборку по умолчанию.

Ctrl+C только выставляет флаг (`io::should_stop()`); долгие программы
обязаны его проверять и сами возвращать `Exit::Interrupted` — вытеснения
нет, прерывание не может "убить" программу.

## Память

| Виртуальный адрес | Размер | Что |
|---|---|---|
| `0x4444_4444_0000` | 1 МБ | куча ядра (`#[global_allocator]`) |
| `0x6000_0000_0000` | 512 ГБ (одна запись P4) | user-область процесса: ELF, стек под `+1 ГБ` |
| `0x5555_5555_0000` | 1 МБ | область данных tmpfs (2048 блоков по 512 байт) |

Обе области при старте маппятся на свободные физические фреймы одной
функцией `memory::map_region` и дальше не растут.

## tmpfs

Файловая система в памяти, плоская (без каталогов). Устроена по
компромиссной схеме:
- **данные файлов** — в отдельной области, разбитой на блоки по 512 байт;
  какие блоки заняты, отмечает битовая карта (1 бит на блок);
- **метаданные** — в куче: `BTreeMap` "имя → inode" (размер + список
  номеров блоков) и таблица открытых файлов.

Метаданные ограничены сверху: не больше 64 файлов, имена до 32 символов,
не больше 16 одновременно открытых файлов. Поэтому их расход кучи мал и
предсказуем, а нехватка места под данные — обычная ошибка `NoSpace`, а не
паника ядра.

Программы работают с файлами через `libpafos::fs`: `File`
(`open`/`read`/`write`, закрытие автоматически при `Drop`), `create`,
`remove`, `entry_at`, `stats`. Данные всегда копируются в буфер программы, ссылки на
внутренности ядра наружу не отдаются — API переживёт переход на ring 3.
Файл создаётся только явно, `fs::create` (если имя занято — `AlreadyExists`);
`File::open` файлов не создаёт ни в каком режиме (`NotFound`). Режимы открытия:
`Read`, `Write` (обнулить и писать с начала), `Append` (дописывать в конец).
Файл может быть открыт только одним дескриптором одновременно (иначе `Busy`).

## Структура

```
src/                ядро
  main.rs           точка входа (entry_point!), запуск оболочки в цикле
  lib.rs            библиотечный крейт: инициализация, test runner
  vga_buffer.rs     вывод текста в VGA text buffer (0xb8000)
  serial.rs         вывод в serial-порт (для тестов/отладки)
  gdt.rs            GDT (сегменты ядра и ring 3) + TSS (стек double fault, RSP0)
  interrupts.rs     IDT, обработчики исключений, PIC, таймер, клавиатура
  clock.rs          PIT на ~100 Гц, время с запуска
  memory.rs         пэйджинг, аллокатор кадров со списком свободных
  allocator.rs      куча (global allocator) поверх пэйджинга
  input.rs          очередь ввода с клавиатуры + флаг Ctrl+C
  tmpfs.rs          файловая система в памяти
  syscall.rs        диспетчер системных вызовов
  programs.rs       реестр программ (имя → вшитый ELF)
  process.rs        ring 3: загрузка ELF, адресное пространство, вход/выход,
                    уровни вложенности
build.rs            сборка ring 3 программ (вложенный cargo)
abi/                pafos-abi: контракт ядро ↔ программы
libpafos/           библиотека для программ
programs/
  shell/            оболочка (ring 3)
  calc/             калькулятор (ring 3; lib.rs — вычислитель для тестов)
  time/             время работы системы (ring 3)
  fault/            нарочно падает: проверка изоляции (ring 3)
  timer/            секундомер с меткой в файле `timer` (ring 3)
x86_64-pafos.json   описание target-платформы (bare metal x86_64)
tests/
  basic_boot.rs     базовая проверка загрузки
  should_panic.rs   проверка, что паника действительно происходит
  stack_overflow.rs проверка double-fault handler-а на переполнении стека
  tmpfs.rs          файлы через libpafos: запись/дозапись, ошибки, полный диск
  syscalls.rs       диспетчер: неизвестный вызов, плохие fd и указатели, exec
  programs.rs       часы, calc, time, timer; ring 3: падения, указатели,
                    куча, утечки кадров
```
